# Спецификация проекта автосалона

## Назначение

Проект представляет собой локальное desktop-приложение для учета работы автосалона. Приложение помогает вести справочники автомобилей, клиентов, сотрудников и поставщиков, оформлять продажи, бронирования, тест-драйвы, сервисные заявки, формировать текст договора продажи и получать SQL-отчеты по данным.

Основная цель проекта - показать не только рабочий Tkinter-интерфейс, но и оформленный инженерный артефакт: структуру приложения, отдельное переиспользуемое ядро, проверяемую SQLite-модель, автоматические тесты, воспроизводимые команды и документацию.

## Границы системы

Входит в систему

- графическое приложение на Tkinter;
- локальная SQLite-база `data/dealership.db`;
- SQL-схема и демонстрационные данные из `sql/schema.sql` и `sql/seed_data.sql`;
- шаблон договора из `templates/contract_template.txt`;
- сохранение сформированных договоров в `contracts/`;
- переиспользуемые helper-функции и правила валидации в `packages/dealership_core`;
- автоматические проверки в `tests/`.

Не входит в текущую версию

- многопользовательский доступ с авторизацией;
- сетевой сервер или web-интерфейс;
- интеграция с внешними платежными системами;
- отправка договоров по email;
- синхронизация с реальными CRM, складами или бухгалтерией;
- полноценный складской учет запчастей.

## Основные сущности

### Поставщик

Таблица `suppliers`.

Поставщик хранит название организации или источника поступления автомобиля и контактную информацию. Автомобиль может ссылаться на поставщика. При удалении поставщика ссылка у автомобиля сбрасывается в `NULL`, чтобы не удалять сам автомобиль.

### Автомобиль

Таблица `cars`.

Автомобиль является центральной сущностью учета. Для него фиксируются поставщик, марка, модель, год, пробег, цвет, цена и статус.

Допустимые статусы

- `доступна`;
- `забронирована`;
- `продана`.

Цена и пробег не могут быть отрицательными. Год выпуска должен быть не меньше 1900.

### Клиент

Таблица `clients`.

Клиент хранит имя, телефон и email. Телефон обязателен и уникален. Email также уникален, если указан.

### Сотрудник

Таблица `employees`.

Сотрудник хранит имя, должность и зарплату. Зарплата не может быть отрицательной. Сотрудник участвует в продажах, бронях и тест-драйвах.

### Продажа

Таблица `sales`.

Продажа связывает автомобиль, клиента и сотрудника. Для продажи хранятся дата, номер договора, цена продажи, статус оплаты, способ оплаты, дата оплаты и путь к файлу договора.

Один автомобиль может быть продан только один раз. После вставки продажи SQLite-триггер переводит автомобиль в статус `продана`. Если для этой машины была активная бронь, она переводится в статус `завершена`.

Допустимые статусы оплаты

- `ожидает оплаты`;
- `оплачено`;
- `отменена`.

### Бронь

Таблица `reservations`.

Бронь связывает автомобиль, клиента и сотрудника. Для брони хранятся дата создания, дата окончания и статус.

Допустимые статусы

- `активна`;
- `завершена`;
- `отменена`.

После вставки активной брони SQLite-триггер переводит автомобиль в статус `забронирована`.

### Тест-драйв

Таблица `test_drives`.

Тест-драйв связывает автомобиль, клиента и сотрудника. Для него фиксируются дата и результат. Результат используется как краткий итог общения с клиентом после поездки.

### Сервисная заявка

Таблица `service_orders`.

Сервисная заявка относится к конкретному автомобилю. В ней фиксируются описание работы, стоимость и статус.

Допустимые статусы

- `новый`;
- `в работе`;
- `завершен`;
- `отменен`.

Стоимость не может быть отрицательной.

## Пользовательские сценарии

### Просмотр справочников

Пользователь открывает таблицы автомобилей, клиентов, сотрудников или поставщиков. Приложение показывает записи в табличном виде. Пользователь может добавить, изменить или удалить запись через форму.

Критерий результата следующий - данные отображаются из SQLite, изменения сохраняются в базе, ограничения схемы не позволяют сохранить некорректные значения.

### Продажа автомобиля

Последовательность оформления продажи и формирования договора показана в sequence diagram:

- editable source: `docs/diagrams/sales-sequence.drawio.xml`;
- PNG preview: `docs/diagrams/exports/sales-sequence.png`.

![Sales sequence diagram](diagrams/exports/sales-sequence.png)

Пользователь открывает таблицу автомобилей, выбирает доступный автомобиль и нажимает кнопку продажи. Приложение подставляет автомобиль, дату, номер договора, цену, статус оплаты и способ оплаты. После сохранения создается запись продажи и формируется договор.

Критерий результата

- продать можно только автомобиль со статусом `доступна`;
- цена продажи не может быть отрицательной;
- дата продажи должна быть заполнена в формате `YYYY-MM-DD`;
- автомобиль получает статус `продана`;
- активная бронь по этой машине завершается;
- файл договора сохраняется в `contracts/`, а путь записывается в `sales.contract_file`.

### Формирование договора по продаже

Пользователь открывает таблицу продаж и выбирает продажу. Приложение берет данные продажи, автомобиля, клиента и сотрудника, подставляет их в шаблон договора и сохраняет текстовый файл.

Критерий результата - договор содержит номер договора, данные клиента, автомобиль, цену, способ оплаты и путь к файлу договора сохраняется в базе.

### Бронирование автомобиля

Пользователь создает запись брони для автомобиля, клиента и сотрудника. Если бронь активна, база переводит автомобиль в статус `забронирована`.

Критерий результата

- дата брони обязательна;
- активная бронь меняет статус автомобиля на `забронирована`;
- доменное правило о том, что дата окончания не должна быть раньше даты брони, вынесено в reusable core и покрыто unit-тестами.

### Запись тест-драйва

Пользователь создает запись тест-драйва для автомобиля, клиента и сотрудника, указывает дату и результат.

Критерий результата

- дата тест-драйва обязательна;
- доменные правила о формате даты и непустом результате вынесены в reusable core и покрыты unit-тестами.

### Учет сервисных заявок

Пользователь добавляет сервисную заявку по автомобилю, указывает описание, стоимость и статус.

Критерий результата - стоимость не может быть отрицательной, статус должен быть одним из допустимых значений.

### Просмотр отчетов

Пользователь открывает окно отчетов, выбирает отчет, при необходимости вводит параметры и запускает SQL-запрос.

В текущей версии доступны отчеты по

- доступным автомобилям;
- клиентам, сотрудникам и поставщикам;
- активным броням;
- количеству машин по статусам;
- продажам за период;
- общей сумме продаж;
- продажам по менеджерам и способам оплаты;
- популярным маркам по продажам;
- сервисным заявкам;
- тест-драйвам без продажи;
- договорам, которые уже сформированы или еще отсутствуют.

Критерий результата - отчет выполняется с параметрами пользователя, результат отображается в таблице, ошибки SQL или пустые параметры показываются через сообщение об ошибке.

## Бизнес-правила и ограничения

| Правило | Где реализовано или проверяется |
| --- | --- |
| Автомобиль нельзя продать, если он не `доступна`. | `packages/dealership_core/validators.py`, `app/ui_tables.py`, unit tests. |
| Цена автомобиля, цена продажи, зарплата и стоимость сервиса не могут быть отрицательными. | `sql/schema.sql`, unit/smoke/integration tests. |
| Один автомобиль не может иметь две продажи. | `sales.car_id UNIQUE`, integration tests. |
| Продажа переводит автомобиль в статус `продана`. | SQLite trigger `set_car_sold_after_sale`, integration tests. |
| Продажа завершает активную бронь того же автомобиля. | SQLite trigger `complete_reservation_after_sale`, integration tests. |
| Активная бронь переводит автомобиль в статус `забронирована`. | SQLite trigger `set_car_reserved_after_reservation`, integration tests. |
| Дата окончания брони не должна быть раньше даты начала. | `packages/dealership_core/validators.py`, unit tests. |
| Даты в core-валидации должны использовать ISO-формат `YYYY-MM-DD`. | `packages/dealership_core/validators.py`, unit tests. |
| Имя файла договора должно быть безопасным для файловой системы. | `packages/dealership_core/helpers.py`, unit tests. |

## Нефункциональные требования

- Проект должен запускаться локально через Python 3 и Tkinter.
- Основные проверки должны выполняться командой `make check`.
- Тесты не должны зависеть от production-базы. smoke и integration tests используют временную SQLite-базу в памяти.
- Переиспользуемая логика должна находиться отдельно от GUI в `packages/dealership_core`.
- GUI-слой должен использовать core-правила вместо дублирования доменной логики.
- Локальные базы, договоры, кэши и заметки проекта не должны попадать в Git.
- Документация должна объяснять предметную область и соответствовать реальным таблицам, сценариям и тестам.

## Проверка требований

Текущее покрытие требований обеспечивается следующими артефактами:

- `tests/smoke/test_database_smoke.py` проверяет создание схемы, seed-данные, выполнение отчетов, рендер договора и отказ схемы принять отрицательную цену.
- `tests/unit/test_core_helpers.py` проверяет форматирование денег, целых чисел и безопасное имя договора.
- `tests/unit/test_core_validators.py` проверяет позитивные и негативные сценарии доменной валидации.
- `tests/integration/test_sqlite_sales_reservations.py` проверяет SQLite-сценарии продажи и бронирования.
- `Makefile` дает единую команду проверки через `make check`.
